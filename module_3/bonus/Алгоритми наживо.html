Алгоритми наживо

Повний інтерактивний гайд з алгоритмів і структур даних курсу: від Big O і пошуку до графів. Кожен алгоритм показано трьома синхронними шарами — схема кроків, рух даних у структурі й рядок коду Python, що виконується саме зараз. «Крок →» — вручну, «▶ Старт» — автоматично. Внизу кожної теми — де цей алгоритм уже реалізовано: у Python і CPython, NumPy, pandas і scikit-learn, Redis, PostgreSQL, Neo4j, Django, FastAPI та Pydantic.

Карта гайду

Тут зібрано всі алгоритми й структури даних курсу — від практикумів П1–П6 до бонусних уроків модуля 3. Кожен розділ відповідає на одне питання: як знайти, як упорядкувати, як зберігати, як обійти зв'язки, як обрати найкраще. Обирай тему на карті або у верхньому меню.

Як працювати з кожною темою

  1. 🔮 Прогноз. Перш ніж запускати, дай відповідь на питання під заголовком. Розгорни відповідь лише після цього.
  2. Крок за кроком. Натискай «Крок →» і стеж за трьома шарами: схема кроків, дані, підсвічений рядок коду.
  3. Зміни дані. Інший вхід, інший розмір, найгірший випадок — де алгоритм ламається чи сповільнюється?
  4. Знайди готове. Блок «Уже реалізовано» показує, який інструмент Python, бібліотека, база даних чи фреймворк робить те саме, як він улаштований усередині, — із прикладом виклику.
  5. Повернись у курс. Внизу кожної теми — посилання на урок, де цей алгоритм розв'язує задачу диспетчерської.

Роадмап: від «хочу програму» до алгоритму

Алгоритми вчать не заради самих алгоритмів. Кожен із них відповідає на якесь питання, яке рано чи пізно ставить твоя програма: як швидко знайти, як упорядкувати, як обрати найкраще, як пройти зв'язки. На цій вкладці є чотири сторінки, які варто читати по черзі: роадмап (у якому порядку вчити і що після кожного етапу ти вже вмієш будувати), «Що хочу побудувати» (обираєш проєкт і бачиш, які алгоритми потрібні на кожному його кроці), «Як обрати алгоритм» (покроково, від питання до інструмента) і «Як писати програму» (метод: гіпотеза, вимір, перевірка).

🔮 Прогноз: ти пишеш Telegram-бота. Користувач надсилає слово, бот має відповісти, чи є воно в списку з 200 000 заборонених слів. Перевірка word in banned_list — це добре чи погано?

Погано: in для списку переглядає елементи по черзі, тобто до 200 000 порівнянь на кожне повідомлення (O(n)). Якщо один раз зробити banned = set(banned_list), перевірка займатиме сталий час (O(1) у середньому). Саме таке рішення — «яку структуру даних обрати» — і є практичною користю алгоритмів. Як рухатися по курсу

1. Задачащо програма має робити для людини

Власну реалізацію пишуть, щоб зрозуміти алгоритм. У робочій програмі майже завжди беруть готову. Розуміння потрібне, щоб обрати правильну і знати, скільки вона коштує.

Що хочу побудувати

Як писати програму: науковий метод

Щоб програма була «згідно з наукою», не треба вгадувати, який алгоритм швидший. Треба поставити гіпотезу, перевірити її вимірюванням і порівняти з простим рішенням, правильність якого очевидна. Це той самий цикл, що в будь-якій науці: гіпотеза → експеримент → вимір → висновок.

Дев'ять кроків

  1. Сформулюй вхід і вихід. Що приходить (тип, приклад, розмір n) і що має вийти. Якщо не можеш написати одним реченням — задача ще не зрозуміла.
  2. Розв'яжи 2–3 приклади вручну. Обов'язково граничні випадки: порожні дані, один елемент, дублікати, від'ємні числа, вже впорядковані дані.
  3. Напиши найпростіше правильне рішення. Навіть O(n²) перебором. Це твій еталон: з ним ти порівнюватимеш усе швидше.
  4. Напиши тести. assert або pytest для прикладів із кроку 2. Додай перевірку на випадкових даних: швидке рішення має давати той самий результат, що й еталон.
  5. Оціни складність. Скільки кроків для n = 10⁶? Використай класи складності: при 10⁸ простих операцій за секунду O(n²) для n = 10⁶ — це години.
  6. Виміряй. timeit для n = 10³, 10⁴, 10⁵. Якщо n зросло вдесятеро, а час — у сто разів, це O(n²). Вимір перевіряє твою гіпотезу про складність.
  7. Знайди вузьке місце. python -m cProfile -s cumtime script.py показує, де справді йде час. Не оптимізуй навмання.
  8. Заміни структуру або алгоритм. Список → множина, повторне сортування → купа, перебір → бінарний пошук. Спершу шукай готове: стандартна бібліотека, пакет, індекс у базі даних. Прожени ті самі тести.
  9. Запиши рішення. У коментарі чи README: чому ця структура, яка складність, при якому n вона перестане працювати.

Шаблон: еталон, швидке рішення, перевірка, вимір

Задача: чи є в списку дублікати. Цей шаблон підходить для будь-якої теми гайду — заміни дві функції.

import random
import timeit

def has_dup_slow(items):            # еталон: очевидно правильний, O(n²)
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                return True
    return False

def has_dup_fast(items):            # гіпотеза: множина дає O(n)
    seen = set()
    for x in items:
        if x in seen:
            return True
        seen.add(x)
    return False

# 1. Правильність: граничні випадки + 500 випадкових порівнянь з еталоном
for case in ([], [1], [1, 1], [1, 2, 3], [-1, 2, -1]):
    assert has_dup_fast(case) == has_dup_slow(case), case
for _ in range(500):
    data = [random.randint(0, 50) for _ in range(random.randint(0, 30))]
    assert has_dup_fast(data) == has_dup_slow(data), data
print("тести пройдено")

# 2. Вимір: як росте час при зростанні n (дані без дублікатів — найгірший випадок)
for n in (500, 1000, 2000):
    data = list(range(n))
    slow = timeit.timeit(lambda: has_dup_slow(data), number=3)
    fast = timeit.timeit(lambda: has_dup_fast(data), number=3)
    print(f"n={n:5}  еталон {slow:.4f} с   множина {fast:.5f} с")
# n подвоюється: час еталона росте приблизно вчетверо (O(n²)), множини — удвічі (O(n))

Чому це важливо: кількість кроків залежно від n

Одна задача, різні алгоритми, одна й та сама машина (умовно 10⁸ простих операцій за секунду). Пересувайте n і дивіться, як розходяться класи складності.

🔮 Прогноз: Алгоритм O(n²) обробляє 1 000 записів за 10 мс. Скільки часу займе 100 000 записів? А алгоритм O(n log n) з тим самим стартом?

n зросло в 100 разів → O(n²) у 10 000 разів довше: ≈ 100 с. O(n log n): ×100 і ще ×(log 100 000 / log 1 000 ≈ 1,67) → ≈ 1,7 с.

Для n = 10⁶ алгоритм O(n²) потребує 10¹² операцій, тобто кілька годин, а O(n log n) — близько 20 мільйонів операцій, тобто частки секунди. Різниця між ними — це лише вибір алгоритму.

Ключова думка

Один результат → багато шляхів. Різниця між ними — у швидкості та ресурсах. Алгоритми — це не про код, а про ефективний спосіб мислення: правильно обрана структура даних (черга, стек, словник) часто і є алгоритмом.

Два правильні рішення, різна ціна

Диспетчер перевіряє, чи не потрапив номер поїздки в журнал двічі. Перше рішення порівнює кожну пару номерів. Друге пам'ятає побачені номери в set. Обидва дають правильну відповідь — але при подвоєнні журналу перше робить учетверо більше роботи, а друге — лише вдвічі.

Пари: 50·49/2 = 1 225 → 500·499/2 = 124 750, тобто приблизно у 100 разів більше (n²). З set: 50 перевірок → 500, тобто у 10 разів (n). Перевір нижче в таблиці подвоєння.

Два вказівники: ваучер на 500 грн

  
Клієнт має ваучер на 500 грн і хоче витратити його рівно на дві поїздки. Ціни відсортовані. Перебір усіх пар — n(n−1)/2 перевірок. Два вказівники стартують з обох кінців. Якщо сума замала, ліву (найменшу) ціну відкидаємо: навіть з найбільшою з решти вона не дає 500. Якщо завелика — відкидаємо праву. Кожна перевірка відкидає одну ціну, тому перевірок не більше ніж n − 1.

  
🔮 Прогноз: скільки перевірок знадобиться для цін [120, 150, 180, 230, 270, 320, 410] і цілі 500?

LRU-кеш: ціни маршрутів без повторних запитів

  
Ціну маршруту диспетчерська отримує від повільного зовнішнього сервісу. Популярні маршрути запитують знову й знову, тож ціни варто кешувати, але пам'ять обмежена: тут лише 3 записи. Коли місця немає, LRU (Least Recently Used) викидає той запис, яким найдовше не користувались. OrderedDict поєднує словник (пошук за O(1)) і двобічний зв'язний список (порядок використання). Ліворуч лежить найдавніший запис, праворуч — найсвіжіший.

Обхід графа: BFS і DFS

  
Той самий граф, той самий стартовий вузол A. BFS (пошук у ширину) тримає сусідів у черзі FIFO і розходиться хвилею по рівнях, тому першим знаходить найкоротший шлях. DFS (пошук у глибину) тримає їх у стеку LIFO і занурюється по одній гілці до кінця. Стежте за вмістом черги і стека під кожним графом: саме структура даних визначає порядок обходу.

Алгоритм Дейкстри: найшвидший маршрут таксі

  
Таксі треба доїхати між районами міста за найменшу кількість хвилин. BFS тут не підходить: він рахує переходи, а дороги мають різну тривалість. Дейкстра щоразу дістає з купи найближчий ще не оброблений район і пробує покращити відстані до його сусідів — це «релаксація» ребра. Поки всі ваги невід'ємні, район, вийнятий з купи першим, уже має остаточну найменшу відстань.

  
🔮 Прогноз: з Подолу (A) до Центру (B) є пряма дорога 6 хв. Чи вона найкраща?
Ні. Через Лук'янівку (E) виходить 2 + 3 = 5 хв. Дейкстра спершу запише B = 6, а коли обробить E, «релаксує» ребро E–B і покращить відстань до 5. Тому відповідь з'являється лише тоді, коли вузол дістали з купи, а не коли вперше побачили.

Беллман–Форд: від'ємні ваги й від'ємні цикли

  
Тепер вага ребра — це вартість поїздки для водія, і на ділянці B→A діє знижка: −3. Дейкстра з від'ємними ребрами може помилитися. Беллман–Форд простіший і повільніший: він V−1 разів проходить весь список ребер і релаксує кожне. За раунд k знаходяться всі найкращі шляхи з не більше ніж k ребер. Ще один, контрольний прохід виявляє від'ємний цикл — петлю, якою можна «заробляти» безкінечно.

Усі 4 (V − 1). Відстань просувається лише на одне ребро за раунд, бо ребра, ближчі до старту, оброблюються останніми.
